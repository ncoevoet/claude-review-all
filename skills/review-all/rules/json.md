# JSON rules

JSON defect deltas: schema/key correctness and accidentally committed secrets. Narrow scope — no style opinions.

#### Schema & keys
- Key renamed or removed that a consumer elsewhere in the diff (or codebase) still reads by the old name
- Field type changed (string to number, scalar to array) in a way that breaks a strict-typed consumer
- Duplicate key in the same object — most parsers keep only the last, silently dropping the first
- Array-vs-object shape change that breaks a consumer indexing by position or key

#### Secrets & credentials
- Literal API key, token, password, or private key value committed in a config/fixture JSON file
- Connection string with an embedded credential (`user:password@host`) committed as a literal value
- Base64-looking blob in a field named `key`/`secret`/`token`/`credential` with no placeholder marker

#### Do not report
- A value change in a `*.snapshot.json`/golden-fixture file explicitly meant to capture output
- Key reordering with no consumer that depends on order
- A placeholder value (`"TODO"`, `"changeme"`, `"xxx"`) already recognizable as a placeholder, not a real secret
- Autogenerated lockfile diffs (`package-lock.json`, `yarn.lock`, etc.)
- A new optional key added with a consumer that already defaults missing keys safely
